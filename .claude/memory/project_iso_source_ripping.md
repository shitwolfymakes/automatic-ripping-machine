"ISO ripping" in v3 is ambiguous and the two meanings point opposite ways: `rip_presets.output_mode = 'iso'` produces an ISO *as output* from a disc; **ISO-source ripping** (this entry) rips *from* an existing `.iso` *as input* through the normal scan→identify→rip pipeline. Always disambiguate.

**What's actually built (supersedes the earlier "clone the transcode dispatcher" plan below the line):** an ISO rip is a **temporary virtual drive**, not a cloned `rip_tasks` table.

- `drives` gained `kind` (`optical`|`virtual`), `source_kind` (`iso`, later `folder`) and `source_path` (relative to the ISO library), plus a `retired` lifecycle value (migration `0041_virtual_drives`). `POST /api/iso/rips` creates a virtual `Drive` row (`enrolled`), and `ripper_manager.ensure_running(drive)` spawns its ripper container exactly like a physical drive's: the same container spec machinery, with different mounts/env (the ISO file read-only at `/source/<name>`, no device access).
- The ripper's **source mode** (`ARM_SOURCE_PATH` / `ARM_SOURCE_KIND` / `ARM_SOURCE_SESSION_ID`) replaces the old `ARM_MANUAL_TRIGGER_ISO` test hook. It registers by drive id through the **same** endpoints a physical ripper uses (register, heartbeat, identify, rip-start, rip-complete); there is no separate claim/heartbeat handshake and no `rip_tasks` table. It runs `handle_manual_trigger` once (bypassing `auto_rip_on_insert`, since the operator started it explicitly) and exits when the job ends.
- Cleanup is **one backend watchdog** (`sweep_virtual_drives`, every 30s plus once at boot before `reconcile_enrolled_rippers`), not a stale-claim sweep: it retires a virtual drive and removes its container once the container exits/dies/disappears, failing the job first if it wasn't already terminal. `DELETE /api/iso/rips/{id}` cancels through the existing job-abandon path and retires immediately.
- The concurrency cap is a UI setting, `config.max_parallel_iso_rips` (Settings > Ripping, 1..8, default 1), not a `MAX_PARALLEL_*` env var.
- The UI's old **Import wizard** (`ImportWizard.svelte`, `IngressBrowser.svelte`, `import-jobs.ts`) is deleted. The gear menu's **"Rip from ISO"** item opens an `IsoPicker` slide-over that calls `GET /api/iso/library` and `POST /api/iso/rips` directly.

- **Extract fallback (2026-10-02):** when MakeMKV lists no titles from the image itself (DVDFab UDF 2.50 backups SIGSEGV `makemkvcon iso:`), the ripper unpacks it with `7z x -tudf` into `/raw/.iso-extract/<drive_id>/<stem>/` (`arm_ripper/iso_extract.py`) and `makemkv_source_url` then answers `file:<folder>` for both scan and rip. Mount was rejected (needs SYS_ADMIN + loop + AppArmor). An image with no titles even unpacked FAILS at rip-start (like a disc) — the automatic switch to the full-disc dump session was removed 2026-10-02 at the owner's request ("it should show up just like a disc with tracks"); the dump session only runs when the operator picks it. Cleanup: ripper on pipeline exit + `retire_virtual_drive` backstop.

- **Rip from folder (2026-10-02):** `source_kind=folder` is built: disc folders (BDMV/VIDEO_TS at root) in the same ISO library, listed flat by `GET /api/iso/folders` (depth 8, 10k-folder budget), started through the same `POST /api/iso/rips`, read by MakeMKV as `file:`. `is_file_source` (ISO or folder) is the "no real drive" check in the ripper. UI: gear menu → IsoPicker `mode="folder"`.

**Why not the dispatcher clone:** the physical-ripper machinery (drive lifecycle, register/heartbeat, identify/rip endpoints, reconcile-on-boot) already does almost everything a task table plus claim handshake would have reinvented. A virtual drive is a thin adapter into that machinery instead of a parallel system.

Still true from the original directive: **ISO rippers are ephemeral, spawned on demand, never a persistent `arm-ripper-iso` daemon.** The Docker socket is already mounted into the backend for transcode spawns, so no new privilege is taken on. The pipeline downstream of scan is source-blind and reused verbatim (identify, review hold, rip-start, rip-complete, transcode, naming). The ISO library is a server-side directory (`ARM_HOST_ISO_LIBRARY_PATH`, mounted read-only); browser upload is still deferred, and extracted disc folders (`source_kind=folder`) are the planned next source kind.
